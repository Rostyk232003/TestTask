# Історія промптів: Strategy Pattern для розрахунку вартості оренди

## Стан: [Активна]

## Версія: v1.2

## Дата: 2026-09-10

## Контекст

Мета фічі — реалізувати Strategy Pattern у рамках Clean Architecture для розрахунку вартості оренди конференц-залів з урахуванням часу бронювання та додаткових послуг.

## Вхідні вимоги

- Зал A: 50 осіб, базова вартість 2000 грн/год.
- Зал B: 100 осіб, базова вартість 3500 грн/год.
- Зал C: 30 осіб, базова вартість 1500 грн/год.
- Послуги: Projector 500, Wi-Fi 300, Sound 700.
- Правила часу:
  - 06:00–09:00: -10%
  - 09:00–18:00: базова ставка
  - 12:00–14:00: +15%
  - 18:00–23:00: -20%
- Вартість оренди обчислюється із залу + послуг + часові модифікатори.
- Якщо бронювання перетинає декілька часових слотів, кошторис розбивається на години і підсумовується.

## ToT-вибір варіантів

### Вариант V1 — Проста реалізація через switch/if у сервісі

Плюси:

- швидко реалізувати;
- мінімум абстракцій.
  Мінуси:
- погано розширюється;
- порушує Open/Closed Principle;
- логіка стає важкою для підтримки.

### Вариант V2 — Strategy Pattern + PricingContext + TimeSlotPricingStrategy

Плюси:

- чистий підхід до заміни алгоритму;
- добре відповідає UML і патерну Strategy;
- легко розширювати нові правила або часові сегменти;
- узгоджується з SOLID.
  Мінуси:
- трохи більше коду на старті;
- потрібно чітко розділити доменну логіку та інфраструктурну реєстрацію.

### Вариант V3 — Rule Engine / Policy catalog

Плюси:

- дуже гнучко для великої кількості правил;
- зручно для складної аналітики.
  Мінуси:
- надто складний для поточної задачі;
- перевищує потреби MVP;
- менш прозорий для підтримки та навчання.

## Рекомендований вибір

Обираємо V2: `IPricingStrategy` + `PricingContext` + `TimeSlotPricingStrategy` + `FlatPricingStrategy`.

Причина:

- це пряме відображення UML-діаграми;
- реалізує патерн Strategy за стандартом refactoring.guru;
- відповідає вимогам Clean Architecture і SOLID;
- легко інтегрується з `Booking` і `HallService`.

## Промпт для подальшого виконання

Виконуємо: Реалізувати фічу Strategy Pattern для розрахунку вартості оренди конференц-залів на .NET 8 у рамках Clean Architecture.

### Вимоги

1. Створити рішення/проєкт у поточній структурі:
   - Domain
   - Application
   - Infrastructure
   - API
2. Реалізувати патерн Strategy, відповідно до UML: `IPricingStrategy`, `PricingContext`, `TimeSlotPricingStrategy`, `FlatPricingStrategy`.
3. Логіка розрахунку має бути в Domain/Application шарі, а не в API контролері.
4. На вході приймати:
   - `hallBaseRate`
   - `startTime`
   - `durationHours`
   - `servicesCost`
5. На виході повертати `decimal` загальної вартості.
6. Реалізувати правила:
   - 06:00–09:00: -10%
   - 09:00–18:00: 0%
   - 12:00–14:00: +15%
   - 18:00–23:00: -20%
7. Якщо бронювання охоплює кілька часових інтервалів, розбити його по годинах і підсумувати вартість кожної години окремо.
8. Додати підтримку вартості додаткових послуг: Projector 500, Wi-Fi 300, Sound 700.
9. Забезпечити чіткий біндінг через DI у API.
10. Додати unit-тести для сценаріїв:

- стандартна година;
- ранкова годинна знижка;
- пікова година з націнкою;
- вечірня знижка;
- перетин кількох слотів в одному бронюванні;
- комбінація з додатковими послугами.

11. Дотримуватися SOLID, чистого коду та стандартів проєкту:

- `var` не використовувати;
- всі ціни/коефіцієнти винести в `Helpers` або `Constants`;
- публічні методи та DTO повинні мати XML-коментарі.

12. Не змішувати бізнес-логіку з контролерами.
13. Додати Swagger endpoint для перевірки розрахунку.

### Очікуваний результат

Після реалізації сервіс повинен коректно розраховувати вартість бронювання для залів A/B/C та послуг з урахуванням чинних правил часу.

### Прийняття результату

Результат вважається успішним, якщо:

- збірка проєкту завершується без помилок;
- unit-тести проходять;
- Swagger показує endpoint для розрахунку ціни;
- логіка патерну Strategy реалізована чітко згідно з UML.
