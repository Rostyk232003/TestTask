# Історія промптів: Архітектурний аналіз та вибір варіанту реалізації

## Стан: [Активна]

## Версія: v1.0

## Дата: 2026-09-10

## Контекст

Мета проєкту — реалізувати REST API для бронювання конференц-залів на .NET 8 з дотриманням Clean Architecture, CQRS через MediatR, EF Core + SQLite, а також SOLID/ToT-процедури. На вхід надано план етапів, який загалом відповідає бізнес-сценарію, але потребує коригування для уникнення надто ранньої архітектурної перевантаженості.

## Оцінка наявного плану

План доцільний у цілому, оскільки він покриває:

- доменну модель;
- цінову логіку;
- пошук доступності залів;
- бронювання з контролем конкурентності;
- аналітичні запити;
- API/Swagger/обробку помилок.

Проте є кілька важливих моментів, які краще виправити до початку кодування:

1. Потрібно розмежувати MVP і масштабування.
   - На етапі 1–2 краще реалізувати мінімально достатню бізнес-логіку, а не одночасно всі модулі аналітики та складну фільтрацію.

2. Strategy Pattern має бути застосований до доменної політики, а не до "сирих" часових інтервалів.
   - Краще розглядати не просто 3 інтервали, а `PricePolicy`/`TimeSlotRule` із нормалізацією до domain value objects.

3. CQRS варто вводити лише на складних операціях.
   - Для `CreateHall`, `GetAvailableHalls`, `BookHallCommand` це доречно.
   - Для простих CRUD/пошуку хороший MVC або minimal API також можливий, але в рамках проєкту використання MediatR є вдалим.

4. Specification Pattern треба використовувати строго для реквестів запитів, а не як універсальний контейнер для всієї логіки.
   - Інакше зросте складність і зменшиться читабельність.

5. Конкурентність слід обороняти через `row version` / optimistic concurrency + транзакцію, а не лише через блокування записів як універсальний варіант.
   - Для сценарію бронювання це найкраще поєднання продуктивності і безпеки.

## ToT-вибір варіантів

### Вариант V1 — Повна "Clean Architecture + Full CQRS" з першого дня

Плюси:

- дуже чиста архітектура;
- легко масштабувати проєкт;
- добре відповідає вимогам інструкцій.
  Мінуси:
- висока стартова складність;
- ризик затримки через надто багато абстракцій до запуску MVP;
- складність для швидкої перевірки бізнес-логіки.

### Вариант V2 — Lean MVP + доменнє ядро + цінова політика як перший блок

Плюси:

- швидше досягається працюючий прототип;
- цінова логіка і модель бронювання перевіряються раніше;
- достатньо чисто для SOLID і Clean Architecture;
- легше поетапно розширювати в модулі аналітики.
  Мінуси:
- на початку не все буде "ідеально доведено" до рівня великого проєкту;
- потрібна дисципліна в зберіганні границь шарів.

### Вариант V3 — Domain-first, максимальна модель даних і value objects

Плюси:

- сильний доменний дизайн;
- добре працює для розширення на складні правила ціноутворення;
- ефективно при довгостроковому супроводі.
  Мінуси:
- втрачається швидкість реалізації;
- для цього завдання може бути надмірним;
- ризик перевантаження проєкту абстракціями до модуля бізнес-логіки.

## Рекомендований вибір

Обираємо Вариант V2: Lean MVP + доменне ядро + цінова політика + CQRS масштабування на критичних сценаріях.

Причина:

- він максимально відповідає рекомендаціям документації;
- дає швидкий, перевірений бізнес-результат;
- дозволяє безперервно розширювати архітектуру без переписування бази;
- зберігає чіткий поділ на Domain/Application/Infrastructure/API.

## Керівний план реалізації після вибору

1. Підготувати рішення .NET 8 з шарами Domain, Application, Infrastructure, API.
2. Реалізувати сутності `Hall`, `Service`, `HallService`, `Booking` із базовим доменним станом.
3. Додати `PricePolicy` / `TimeSlotRule` та `IPricingStrategy`.
4. Реалізувати `GetAvailableHalls` query і `BookHallCommand`.
5. Додати `RowVersion`/optimistic concurrency для захисту від подвійного бронювання.
6. Додати аналітику після стабільного MVP.
7. Після успішного наповнення логіки — внести Swagger, FluentValidation, Global Exception Handling.

"Обрано V2 — Lean MVP з доменним ядром і ціновою політикою, оскільки він забезпечує найкращий баланс між SOLID, Clean Architecture та швидким досягненням працюючої бізнес-логіки. Наступний етап: ініціалізація рішення .NET 8, модель домену, PricePolicy, доступність залів і бронювання з optimistic concurrency."
